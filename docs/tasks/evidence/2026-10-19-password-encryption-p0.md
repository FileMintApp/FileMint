# 密码加密保护 P0：AppleArchive、目录往返和密码迁移

日期：2026-10-19。关联[主任务](../2026-10-19-file-encryption-protection.md)。

封板状态：主任务已按用户要求封板。本记录仅保留历史实验与复查材料，不构成重跑探针或推进实现的授权；需用户明确重新开启。

## 结论及证据边界

用户本轮授权独立 P0，重点验证 password 模式、文件夹加解密和统一密码变更后的旧文件迁移。三个重点均已有本机隔离实验结果，**可以继续以 AEA password profile 为候选，但不等于可直接发布产品**。

- 本机 API 的密码长度边界观测为 **20–256 UTF-8 字节**；19／257 被拒绝，20／256 已完整加解密验证。中文、Emoji 可用；字节长度不是强度，32 个空格也被接受。
- 文件内容、嵌套目录、空目录、文件名、mode、修改时间、自定义扩展属性与测试资源叉，在本轮样本及明确字段集下完整往返。Apple CLI 与 Swift API 双向互操作通过。
- 可把旧归档的解密字节流直接送入新密码加密流，不写出明文归档或解密目录作为迁移中间件；输出验证后才能替换。已验证新密码有效、旧密码对新归档失效，未迁移副本仍使用旧密码。
- 错误密码／破坏内容会失败，但晚期失败可能留下已写出的明文；加密容器尾部多余数据也不一定由原生解密自动拒绝。需要私有暂存、完整验证、严格长度检查和独占发布，不能以一次 API 返回为唯一交付条件。

本轮没有 FileMint 产品代码、菜单、设置、持久密码配置、Keychain 写入、生产权限或安装变更。所有密码为源码中明确标记的公开测试字符串；没有收集、记录或使用用户密码。所有读取、改写、重命名和进程终止只作用于本轮新建样本／子进程。没有删除用户原件。

## Password 模式

使用 `ArchiveEncryptionContext(profile: .hkdf_sha256_aesctr_hmac__scrypt__none, compressionAlgorithm: .lzfse)`，以 `setPassword` 设置原始字符串，2 个工作线程。无字符串预哈希、补位、裁剪或替代算法。

| 观察 | 本机结果 | 对产品的影响 |
| --- | --- | --- |
| 短密码 | 0／1／7／8／15／16／17／18／19 字节返回 `invalidValue` | 常见 8–16 位 ASCII 密码无法直接用此 profile |
| 正常范围 | 抽样 20、31、32、33、63、64、127、128、255、256 字节接受；20／256 完整往返 | UI 必须检查 UTF-8 字节数并解释长口令要求；不是所有长度／字符组合穷举 |
| 超长输入 | 257、511、512、513、1023、1024、4096、65536 字节拒绝 | 不能无提示截断 |
| 多字节 | 8 个汉字=24 字节、11 个汉字=33 字节、8 个 Emoji=32 字节均完整往返 | 字符数不能简单当字节数 |
| 弱输入 | 32 个空格接受并可往返 | 框架长度校验不是密码强度策略，产品必须另行约束弱口令 |
| NUL | 32 字节含内部 NUL 的样本可往返；改变 NUL 后的字节解密失败 | 未观察到 C 字符串截断；产品是否允许控制字符另行定义 |
| Unicode 表示 | NFC 与 NFD 的同外观字母各自可往返，交叉密码失败 | 必须明确并版本化输入／规范化规则，不能发布后悄悄改行为 |
| 随机性 | 同内容、同密码两次加密输出 SHA-256 不同 | 证明本次输出非确定，不等于独立密码学安全审计 |

单个原始文件 3,145,745 字节加解密后 SHA-256 一致。原始字节模式不携带原文件名／元数据；产品单文件封装仍应采用明确归档结构，而非据此宣布全部文件元数据已支持。

此次 native KDF 参数安全性、弱密码离线攻击成本、内存清零和设备间校准没有独立审计。操作耗时不能被当成密码抗破解能力证明。

## 文件夹往返

采用 `writeDirectoryContents`，字段集为 `TYP,PAT,DAT,MOD,MTM,XAT`，经 encode → password encryption 流写入。还原为 decryption → decode → extract，全程不启用“忽略权限错误”。

- 样本含 7 个根目录以下条目：4 个文件、3 个目录；有深一层中文目录、两个空目录、空文件、带空格／中文文本、3 MiB 二进制和 metadata 文件。
- Python 独立 manifest 比较相对路径、种类、文件 SHA-256、mode、纳秒修改时间和 xattr 内容摘要，完整相等；自定义文件／空目录 xattr、`com.apple.ResourceFork` 测试载荷都保留。
- 源 manifest 在归档、解密和迁移后再次核对，保持一致。
- Swift 创建的密文经 `/usr/bin/aea decrypt` + `/usr/bin/aa extract` 还原一致；Apple CLI 创建的 profile 5 密文再经 Swift extract 还原一致。两者可能共享系统实现，因此属于互操作证据，不是独立密码学实现互证。
- 密文字节中未发现样本的内部文件名／内容标记；这只证明所查标记不可见，不是完整元数据泄露审计。

未覆盖：顶层根目录命名／所有属性、创建时间、ACL、Finder tags、quarantine、符号链接、硬链接、包、深度／条目极限、路径逃逸、特殊文件、云占位、其他文件系统。不可依据这 7 个条目宣布任意目录完整支持；当前字段集中的 mode 也不是产品还原任意权限的授权。

## 统一密码修改与迁移

直接把“当前密码”换成新字符串后，新密码无法解开旧归档，已实测。可行的候选迁移路径为：

```text
旧归档 + 旧密码
  → 解密字节流（内存块）
  → 新密码加密流
  → 新密文候选
  → 独立完整解密验证／manifest比对
  → 替换本次明确选择的归档
```

迁移不需要把目录解出来再打包。P0 对3 MiB目录归档和64 MiB原始内容都完成了上述流式重加密；前者还原 manifest 一致，后者还原 SHA-256 一致。完整验证在隔离目录落地合成明文以独立比对；生产是否采用验证到摘要接收器仍需实现设计，不能宣称本轮完全没有验证明文。

| 场景 | 结果 |
| --- | --- |
| 已迁移候选 | 新密码可解，旧密码拒绝，源旧归档的密文 SHA-256 不变 |
| 发布 | 只对自建 `live.aea` 副本做替换，新密码可读；保留的“离线旧副本”继续只能按旧版本处理 |
| 中途受控错误 | 复制1 MiB后抛错，不发布候选；旧归档保持，候选虽可能经过 defer 关闭，完整目录还原失败 |
| 中途进程终止 | 64 MiB迁移在候选写入2,115,772字节后向本轮子进程发 SIGTERM（exit=-15）；候选不可解，旧归档摘要不变且仍完整解密 |
| 目标重名 | 独占创建失败，既有 sentinel 输出和源归档都保留 |
| 批次中断状态 | 构造“第1项已经发布新版本、第2项保持旧版本”的两个自建归档；密码矩阵分别是仅新密码有效／仅旧密码有效 |

最后一项是以真实有效密文构造的混合版本状态观察，不是生产批量服务／持久日志的崩溃恢复测试。SIGTERM 是进程级中断，不是断电、文件系统崩溃或 fsync 持久性验证。

产品取舍：修改统一密码应成为显式、可恢复的已知归档迁移任务；显示已迁移／待迁移／离线／失败，不把设置保存等同于全局完成。离线盘、其他位置和备份的旧副本不能被自动撤销；不能在还有旧文件时丢弃旧密码所需的恢复路径。如何保存迁移期间的旧密码材料仍待独立设计，不能从本轮测试字符串推导生产应保存明文密码。

64 MiB本机单次迁移观察约246ms、独立解密约69ms；这只是热缓存可能存在的一次样本，不是稳定性能指标，未测峰值 RSS、GiB级文件或用户取消延迟。
