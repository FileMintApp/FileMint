# FileMint 右键工具调研与迭代建议

调研日期：2026-09-17。本文是产品研究和候选路线，不是已批准的产品规范或发布承诺。

本次查阅了产品官网、开发者文档、App Store 描述及公开反馈，并核对当前仓库的 `specs/SPEC.md`、`specs/HARNESS.md` 和相关实现。没有安装试用这些竞品，也没有进行性能横测。竞品功能以开发者公开资料为依据；成本、优先级和 FileMint 的设计方案是本次研究的判断。

没有找到口径一致的装机量数据，因此下面选取的是具有代表性的成熟产品及相关设计样本，不将其排列称为热门榜单。QSpace、PopClip 和 Windows 工具另作相邻产品参考，不与 Finder 扩展混为一类。

## 建议的演进方向

让用户在当前文件夹，把内容快速变成可用的文件。

这个方向可以容纳场景模板、真实文档模板、剪贴板落盘、项目目录创建和创建后打开，也能延续 FileMint 的原生、离线、无账号、无后台扫描的特点。优先考虑使用频繁、结果明确、可以本地完成、维护成本可控的功能。

最值得投入的基础能力是：**允许同一种文件格式有多个不同用途的模板。** 当前 FileMint 的类型和模板实际上绑定在一起，重复后缀被拒绝；这会限制“会议记录.md”“项目说明.md”“复盘.md”等常见需求。

## FileMint 当前已经具备的能力

以下是当前规范和代码的静态核对结果，不代表本次重新完成了 Finder 实机验收。

- Finder 快速创建与主应用创建面板；工具栏入口已有实现。
- 14 种内置文本格式，按需启用、停用和排序；自定义文本后缀及初始内容。
- 完整文件名与后缀同步、模板内容变量、原样保存主动粘贴的文本。
- 创建后在 Finder 中显示的开关，快速创建和面板创建均有对应调用。
- 应用内键盘操作和新建快捷键。它不等于任意应用中的全局快捷键。
- 同名递增、替换确认、独占创建、目标目录捕获、授权持久化等保护。
- 原生设置、中英文、登录启动、菜单栏及更新流程。

新增规划应建立在这些已有能力上，不重复安排“增加排序”“增加 Finder 工具栏”“创建后显示文件”等工作。

主要代码依据：

- `CorePackage/Sources/FileMintCore/FileTemplate.swift`：当前模板内容为字符串；自定义模板校验拒绝重复后缀。
- `App/FileMint/ContentView.swift`：类型管理及创建后显示开关。
- `App/FileMint/PreferencesModel.swift`、`SharedUI/CustomFileSavePanelController.swift`：创建完成后显示结果。
- `FinderSyncExtension/FileMintFinderSync/FinderSync.swift`：Finder 菜单和工具栏入口。

## 候选功能的优先级

优先级表达推荐先后，成本为基于当前架构的相对估计，没有完成实现验证或排期。P0 为持续质量工作，P1 为下一阶段重点，P2 为后续扩展，P3 为有实际需求后再评估。

| 优先级 | 功能 | 典型使用场景 | 预计成本及关键边界 |
| --- | --- | --- | --- |
| P0 | 首次使用和故障定位更清楚 | 菜单未出现时，用户知道是扩展未启用、目录未授权还是目标不可用 | 中；延续已有状态和权限说明，不能伪造完全磁盘访问检测 |
| P1 | 同后缀多模板、模板复制与预览 | 同时保存会议记录.md、读书笔记.md、README.md | 中；需要拆分格式与模板概念，并迁移旧设置 |
| P1 | 文件名规则和预览 | 创建 `2026-09-17-会议记录.md`、带项目名称的说明文件 | 中；日期时区、递增与用户输入覆盖规则必须明确 |
| P1 | 创建后打开 | 创建笔记后继续写，创建源码后在选定编辑器中打开 | 低至中；已有显示功能，新增打开策略；创建成功但打开失败应分别反馈 |
| P1 | 模板导入导出 | 换电脑恢复模板、分享自己整理的常用模板 | 中；先做本地文件，导入前预览冲突，不迁移机器权限和私有路径 |
| P2 | 从真实文档创建副本 | 使用自己的 Word 周报、Excel 清单、演示文稿作为模板 | 中至高；保存有效原文件并复制，不是给文本换后缀 |
| P2 | 从剪贴板创建文件 | 将截图保存为 PNG，将复制的代码保存为文本 | 文本中、图片中；只有用户主动执行时读取，图片需真正编码 |
| P2 | 当前目录的开发工具入口 | 在 Terminal、iTerm、VS Code 或用户选择的编辑器继续操作 | 中；不同应用的打开目录方式和沙盒约束需验证 |
| P2 | 复制文件名和路径 | 写文档、提交问题、在终端引用文件 | 低至中；若做相对路径，必须有明确基准目录 |
| P2 | 模板分组、固定常用项、搜索 | 模板变多后仍能快速找到需要的项目 | 中；当前已有排序和类型搜索，应在场景模板增长后扩展 |
| P3 | 项目目录模板 | 一次创建文档、素材、交付目录及起始文件 | 高；涉及多文件操作、冲突、取消与部分失败处理 |
| P3 | 快捷指令、Raycast/Alfred 联动 | 从键盘或其他工具调用 FileMint 创建流程 | 中至高；先提供有用户确认的草稿入口，验证目标目录与授权 |
| P3 | 收藏目的地、复制/移动到 | 把刚生成的材料放入常用位置 | 中至高；文件移动引入覆盖、跨卷、云盘等维护成本 |
| 暂缓 | 图片批处理、复杂压缩、批量重命名 | 大批量素材整理 | 中至高；需先证明相较系统功能的具体收益 |
| 暂缓 | 卸载、磁盘清理、重复文件扫描、任意脚本市场 | 全盘维护或通用自动化 | 高且持续；明显扩大权限、支持及维护范围 |

### 最值得优先实现：场景模板

建议允许同一种格式对应多个模板，并分别设置名称、内容、默认文件名和排序。例如：

| 模板名称 | 输出格式 | 默认内容 |
| --- | --- | --- |
| 会议记录 | Markdown | 议题、讨论记录、行动项 |
| 项目说明 | Markdown | 背景、运行方式、注意事项 |
| 问题复盘 | Markdown | 现象、原因、解决过程 |
| 接口示例 | JSON | 用户保存的常用结构 |

这些是建议新增的使用示例，不是已经内置的模板。类型选择器继续负责格式；模板选择负责用途。不能只删除重复后缀校验，还要处理格式默认模板、旧数据迁移及菜单名称消歧。

当前内容变量已经存在。下一步应完善文件名规则的可视化预览，而不是另建一套含义不一致的变量系统。当前 SPEC 中日期变量使用 UTC；面向“今天”的文件名如果引入本地日期，需作为明确的新选项，不应悄悄改变既有模板输出。

### 真实文件模板：扩大受众的自然方向

用户选择一份正常可打开的 `.docx`、`.xlsx` 或其他文档，FileMint 保存模板副本，之后在目标文件夹生成新副本。原模板不被新建操作修改。New File Menu 和 New+ 的公开设计为这种能力提供了参考。

先支持有限、可验证的普通单文件模板；应用文稿包、文件夹模板和特殊元数据另行处理。模板内容可能包含个人信息，分享时应让用户自行检查。模板只作为数据复制，不运行其中的脚本或宏。

这项能力会扩展当前“UTF-8 文本创建”的范围，应先更新 SPEC，并覆盖复制完整性、同名冲突、模板源丢失及旧设置迁移。验收包括实际使用相应应用打开生成的文件，不能只检查扩展名。

### 剪贴板落盘：与日常工作贴近

从 Menuist 的图片粘贴能力可延伸出两个 FileMint 场景：

- 用户主动选择“从剪贴板新建…”，文本进入现有面板，可命名并选择文本格式。
- 用户复制截图后选择相应动作，将图像编码成 PNG，之后可按需求增加 JPEG。

文本路线已有面板粘贴基础，需要评估独立入口能减少多少操作。图片路线是新增能力，需保留像素尺寸、正确处理透明度，并区分“复制了一张图片”与“复制了一个文件”的剪贴板内容。

保持不监听剪贴板的承诺。菜单可以显示固定的“从剪贴板新建…”入口，点击后再读取并判断内容，不要为了动态菜单预览而提前读取正文或图片。

### 创建之后的动作：完成工作流

已有“在 Finder 中显示”，建议扩展为明确的偏好选择，例如保持当前行为、仅创建、创建并打开；后续再考虑按模板指定编辑器。

创建失败与打开失败是两回事。文件已创建而编辑器不可用时，应显示文件已保存，并提供定位入口。脚本或可执行类型不能因通用“打开”而意外执行，应有独立策略；不要模拟按键自动在 Finder 中进入重命名模式作为默认实现。

### 项目目录模板：长期辨识度

New+ 支持从文件夹模板创建对象。FileMint 可以借鉴这个思路，逐步支持用户保存的一组目录和初始文件。例如下面只是建议模板：

```text
客户项目/
├── 01-资料/
├── 02-制作/
├── 03-交付/
└── README.md
```

长期价值来自用户自己的工作习惯。设计、写作、开发、研究各有不同结构，不必全部由维护者内置。先完成单文件模板，再推进目录模板，可复用命名、导入导出及管理界面。

创建目录模板必须预览输出，拒绝路径逃逸，并限制范围。遇到失败时只能清理本次新建且能确认未被用户修改的项目，不能回滚删除已有数据。应用包、符号链接、云端占位文件等需要明确首版是否支持。

## 菜单应该随着功能增长仍然容易使用

Nilesoft 的条件显示和 [PopClip 的上下文动作](https://www.popclip.app/guide/actions) 值得借鉴。以下是 FileMint 的建议，不代表这些工具都采用相同界面：

- 默认继续保持紧凑；用户主动启用附加功能。
- 空白处偏向创建；选中文件后才展示适用的文件操作。
- 多选场景明确操作数量，例如“复制 3 个文件名”。
- 常用项由用户固定，避免自动重排破坏肌肉记忆。
- 文件模板较多时在主应用面板提供搜索，Finder 中保留少数常用项。
- 菜单展开不执行目录扫描、文件哈希或联网查询。

现有 SPEC 不暴露无功能的收藏入口；若未来增加固定常用项，应实现完整行为并更新规范。

Windows 工具可定制的系统菜单范围不应直接作为 macOS 可实现性的证据。Apple 的 [Finder Sync 文档](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Finder.html) 描述了监控目录、扩展菜单与工具栏的边界；应在这些公开能力内扩展 FileMint 自己的入口。QSpace 的高度自定义发生在它自己的文件管理界面中。

## 不急着重复系统已有能力

Apple 已提供 Quick Actions，可按文件类型创建 PDF、旋转及转换图片，并接入快捷指令，见 [Apple 官方说明](https://support.apple.com/guide/mac-help/perform-quick-actions-in-the-finder-on-mac-mchl97ff9142/mac)。

因此，“也有图片转换”本身不足以成为优先理由。若用户确实需要特定格式、固定尺寸预设或更短的步骤，再考虑针对性增强。自建万能压缩、媒体处理、清理扫描等模块则会增加长期依赖维护，建议留待明确需求出现后单独评估。

## 可靠性是持续迭代的一部分

[Menuist 的官方 FAQ](https://github.com/jaywcjlove/rightmenu-master) 讨论了菜单不显示和重复授权；[iRightMouse 的历史更新](https://apps.apple.com/cn/app/id1497428978?mt=12) 包含 iCloud 菜单和资源占用修复。这些是公开的历史问题记录，不表示当前版本仍然存在同样缺陷，也不是发生频率统计。

它们提示 FileMint 应长期维护以下体验：

1. 首次安装后，用户能完成一次实际创建，而不只是看到“设置完成”。
2. 菜单缺失时给出具体下一步；区分扩展状态、目录权限与不可写目标。
3. 桌面背景、Finder 文件夹、外置卷、iCloud 和其他文件提供方分别验证，不笼统承诺“全部支持”。
4. 连续创建、冷启动、更新后、睡眠唤醒后都要有可重复的验证场景。
5. 不随意打开设置、不抢焦点，不让创建后动作打断下一次右键操作。
6. 大文件复制和图片编码可取消、不会阻塞 Finder；错误保留用户输入。

已有 `docs/FINDER_QA.md` 是维护这些场景的良好起点。后续性能指标应先测当前基线，再设定目标；本次没有测量可用于宣称“更快”的数据。

## 建议分三轮推进

**第一轮：把文本创建做得更贴近用途。**

同后缀多模板 → 模板复制和预览 → 文件名规则 → 创建后打开。同步完善首次创建指引和失败说明。每个小版本只交付一个可以独立验收的主要改进。

**第二轮：让个人模板可以积累和迁移。**

本地模板导入导出 → 真实文档模板 → 剪贴板图片落盘。模板格式应有版本号，导入可预览，不自动覆盖已有模板。首期无需云账号或同步服务器。

**第三轮：根据真实需求扩展。**

项目目录模板、模板搜索分组、当前目录编辑器/终端入口、快捷指令和启动器联动。顺序取决于前两轮用户反馈，不能把所有候选功能直接当作承诺。

外部联动需要延续已有安全边界：当前裸 deep link 不允许直接创建文件。优先提供打开预填草稿的方式；若以后引入自动化创建接口，应另行设计明确授权和参数校验。任意用户脚本也不应直接塞入 Finder 扩展进程中运行。

## 让个人维护可以持续

- 建议保留三类公开清单：近期准备做、需要更多场景、暂不考虑，并说明理由。
- 收集需求时先问用户“在哪个文件夹、反复创建什么、目前要走几步”，再讨论按钮名称。
- 判断收益看步骤是否减少、命名和模板是否更少出错、用户是否愿意持续使用；不把功能数量当目标。
- 用户可贡献模板、翻译、文档和复现步骤；先有可审阅的模板分享，再评估脚本或插件生态。
- 延续无遥测边界，通过自愿反馈和可选诊断收集证据。诊断应先展示内容，不默认包含完整路径或文件内容。
- 每轮保留兼容性与文档维护空间；不承诺固定发布日期，以免兴趣项目变成持续交付压力。
- 后续实现遵循仓库 SPEC-first、Harness 和 Finder 实机验证要求；调研阶段不修改功能契约。

推荐先从“同后缀多模板”这个范围明确的改进开始。它能服务现有用户，也为真实文档模板和项目目录模板提供基础。
